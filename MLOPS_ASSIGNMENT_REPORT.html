Problems Faced

Problem 1: API Dockerfile Path Issues

Issue: The API Dockerfile was initially configured to copy files assuming the build context was inside the api/ directory. When building from the project root using docker build -f api/Dockerfile -t mlops-api ., the COPY commands failed because paths were relative to the wrong directory.

Error:

COPY failed: file not found in build context

Root Cause: Docker build context was the project root, but COPY commands expected files relative to api/ directory.

Problem 2: Model Path Resolution in API

Issue: The API application initially looked for the model file at models/model.pkl relative to the API directory, but when running in Docker, the model needed to be in the correct location relative to the working directory.

Error:

Warning: Model file not found at models/model.pkl

Root Cause: Path resolution differed between local development and Docker container environments.

Problem 3: Airflow Volume Mount Paths

Issue: Airflow DAG tasks referenced absolute paths (/opt/airflow/data/dataset.csv) but the volume mounts in docker-compose.yaml needed to ensure data was accessible at those paths.

Error:

FileNotFoundError: Dataset not found at /opt/airflow/data/dataset.csv

Root Cause: Mismatch between volume mount points and hardcoded paths in DAG code.

Problem 4: Dependency Version Conflicts

Issue: Different Python versions (3.9, 3.10, 3.12) used across different components (CI/CD, Docker, local) caused some dependency conflicts, particularly with numpy and pandas versions.

Error:

ImportError: cannot import name 'X' from 'module'

Root Cause: Version incompatibilities between scikit-learn, numpy, and pandas across different environments.

Problem 5: DVC Remote Storage Configuration

Issue: Initially, DVC remote was not properly configured, causing issues when trying to push/pull data versions.

Error:

ERROR: failed to push data to the cloud

Root Cause: Remote storage path not properly initialized or permissions not set correctly.

Problem 6: GitHub Actions Python Version Mismatch

Issue: Local development used Python 3.12, but GitHub Actions workflow specified Python 3.9, causing some test failures due to syntax differences.

Error:

SyntaxError: invalid syntax (Python 3.9 incompatible)

Root Cause: Using Python 3.12-specific features in code that GitHub Actions ran with Python 3.9.

Problem 7: Docker Build Context Size

Issue: Initial Docker builds were slow and large because the entire project directory (including logs, cache, and large files) was being copied into the build context.

Error:

Build context too large

Root Cause: .dockerignore file was not comprehensive enough, including unnecessary files in the build.

Problem 8: Airflow XCom Size Limitations

Issue: Attempted to pass the entire model object through XCom, but Airflow has size limitations on XCom data (default 48KB).

Error:

XCom value too large

Root Cause: Trying to serialize and pass large model objects through XCom instead of using file-based storage.

Fix 8: Airflow Model Storage Strategy

Solution: Changed from XCom to file-based storage for models:

# Before: Trying to pass model through XCom
context['ti'].xcom_push(key='model', value=model)

# After: Save model to file, pass path through XCom
model_path = '/opt/airflow/models/model.pkl'
with open(model_path, 'wb') as f:
    pickle.dump(model, f)
context['ti'].xcom_push(key='model_path', value=model_path)

Result: ✅ Models saved correctly without XCom size limitations.

Learning Summary

1. Version Control with DVC

Key Learnings: - DVC provides powerful data versioning capabilities separate from Git - DVC tracks large files externally while Git tracks small .dvc metadata files - DVC pipelines enable reproducible ML workflows with dependency tracking - Remote storage configuration is crucial for team collaboration

Best Practices: - Always initialize DVC remote storage early - Use dvc repro to run pipelines instead of manual execution - Commit .dvc files to Git, not the actual data files - Use descriptive stage names in dvc.yaml

2. CI/CD with GitHub Actions

Key Learnings: - GitHub Actions provides seamless integration with Git repositories - Workflow files must be in .github/workflows/ directory - YAML syntax requires careful attention to indentation - Matrix builds can test across multiple Python versions - Caching dependencies significantly speeds up CI runs

Best Practices: - Always test workflows locally before pushing - Use actions/checkout@v3 for code checkout - Set up proper Python version matching across environments - Include both unit tests and integration tests - Use linting tools (flake8, pylint) for code quality

Challenges Overcome: - Understanding YAML syntax and GitHub Actions context - Configuring proper Python environment setup - Managing dependency installation in CI environment

3. Docker Containerization

Key Learnings: - Docker provides consistent environments across development and production - Multi-stage builds can reduce final image size - Build context matters - .dockerignore is essential - Layer caching significantly speeds up rebuilds - COPY order affects cache invalidation

Best Practices: - Copy requirements first, install dependencies, then copy code - Use specific base image tags, not latest - Minimize number of layers - Use .dockerignore to exclude unnecessary files - Test containers locally before pushing to registry

Challenges Overcome: - Understanding Docker build context and path resolution - Optimizing Dockerfile for faster builds - Managing different Dockerfiles for different services - Debugging containerized applications

4. Apache Airflow Orchestration

Key Learnings: - Airflow DAGs are Python files that define workflows - Tasks communicate through XCom (limited size) or shared storage - Proper logging is crucial for debugging DAGs - Task dependencies are defined using >> operator - Airflow UI provides excellent visualization and monitoring

Best Practices: - Use descriptive task IDs - Implement proper error handling and retries - Log important information for debugging - Use XCom sparingly (for small data), files for large data - Test DAGs locally before deploying

Challenges Overcome: - Understanding Airflow's execution model - Managing XCom size limitations - Configuring proper volume mounts in Docker Compose - Debugging failed tasks through logs

5. RESTful API Development

Key Learnings: - Flask provides lightweight framework for ML APIs - Model loading should happen at application startup - Input validation is crucial for production APIs - Error handling improves user experience - Health check endpoints are essential for monitoring

Best Practices: - Load models once at startup, not per request - Validate all inputs before processing - Return meaningful error messages - Use proper HTTP status codes - Implement health check endpoints - Support both single and batch predictions

Challenges Overcome: - Managing model loading in different environments - Implementing proper error handling - Designing API response formats - Testing API endpoints

6. AWS Cloud Deployment

Key Learnings: - EC2 instances require proper security group configuration - Docker simplifies deployment on EC2 - S3 provides scalable storage for datasets - Public IP addresses change on instance restart - SSH key management is critical for access

Best Practices: - Use security groups to restrict access - Store Docker images in container registries (Docker Hub, ECR) - Use environment variables for configuration - Implement proper logging for debugging - Set up monitoring and alerts

Challenges Overcome: - Understanding AWS security groups and networking - Configuring EC2 instances properly - Managing Docker containers on remote servers - Testing remote deployments

7. Overall MLOps Practices

Key Learnings: - Reproducibility: Version control for code, data, and models - Automation: CI/CD pipelines catch issues early - Containerization: Ensures consistent environments - Orchestration: Manages complex ML workflows - API Development: Enables model serving - Cloud Deployment: Provides scalability and accessibility

Best Practices: - Start with version control (Git + DVC) - Implement testing early (unit, integration) - Use containers for consistency - Automate everything possible - Monitor and log extensively - Document thoroughly

Challenges Overcome: - Integrating multiple tools and technologies - Managing dependencies across environments - Debugging distributed systems - Balancing development speed with production readiness

8. Problem-Solving Approach

Key Learnings: - Read error messages carefully - they often contain solutions - Check documentation when stuck - Use logging extensively for debugging - Test components in isolation before integration - Version control helps track changes and rollback

Problem-Solving Process: 1. Identify: Understand the exact error or issue 2. Isolate: Reproduce the problem in minimal environment 3. Research: Check documentation, Stack Overflow, GitHub issues 4.
